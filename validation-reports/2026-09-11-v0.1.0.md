# Validation report — nmsbonker 0.1.0

**Date**: 2026-09-11
**Spec**: [`specs/004-tweaks-deploy-rollback-packaging.md`](../specs/004-tweaks-deploy-rollback-packaging.md)
— phase 4 of 4, and with it the 0.1.0 milestone.
**Scope**: built-in tweaks with tunable parameters; the game's own
`GCMODSETTINGS.MXML`; the deploy archive, rollback and undeploy; save backup;
the Tweaks section and the Overview actions in the window; packaging, install
scripts, screenshots and the README.

**Environment**: Go 1.27.1, golangci-lint v2.12.2 (under `GOTOOLCHAIN=go1.26.0`),
Fyne v2.8.1, gopher-lua v1.1.1, MBINCompiler **v7.02.0-pre1** (`dotnet10`, .NET
runtime present), Steam buildid **25233815** (97 paks, 194,531 internal paths),
KDE on Wayland.

---

## Summary

Phase 3 left a builder with a window: it could merge mods, recompile them and
copy a folder into the game. Three things were missing and this phase adds them.

The tool now ships mods of its own — ten AMUMSS scripts written for this project,
embedded, each declaring its tunable numbers in `-- @param` headers so a front
end can offer a labelled slider with a range. Overrides live in `config.json` and
are substituted into an in-memory copy of the script at build time, so the
scripts themselves are never edited and upgrading brings the new script with the
user's numbers still in it.

The deploy is finished. Copying a folder into `GAMEDATA/MODS` was never enough:
the game keeps its own list in `GCMODSETTINGS.MXML`, and a mod with no entry
there — or with the entry off, or with `DisableAllMods` set, which the game does
after a crash — is installed and inert. That file is now written, line by line,
so the byte-order mark, the CRLF endings, the tabs and every property this build
does not understand survive untouched. Every deploy archives what it displaced,
retention five; `rollback` puts one back and archives what was installed;
`undeploy` takes the folder out; `mods-off` is a kill switch that removes
nothing. The first deploy of each run copies the saves out of the Proton prefix,
retention ten, in one direction only.

And it is packaged: `install.sh`, `uninstall.sh`, a desktop entry whose basename
is the Fyne application ID, an icon, `make release`, and a README written for
somebody who has never seen it.

Three things the phase-3 review asked for landed alongside: the Overview's
"Game data version" row is gone (spec 002 R3.4 retired the concept — the game's
MBINs carry no libMBIN version to report), its Compatibility row now reports the
round-trip measurement taken in the background on first load instead of reading
"unknown — not checked yet" for the life of the window, and the symlinked
`GAMEDATA/MODS` state is an action rather than a paragraph.

The gate that matters most is the one that costs nothing to state and would have
caught the worst possible bug here: **the ten embedded tweak scripts decode to
the same `MODIFICATIONS` as their reference copies.** They were copied out of the
reference pipeline and given header comments, and "comments cannot change
anything" is exactly the sort of claim that is true until a stray character lands
inside a change table and produces a subtly different mod that still builds.

## Acceptance criteria

**AC1 — built-ins at their default values reproduce the reference dump, and the
golden suite still passes.** `TestBuiltInsDecodeAsTheReferenceCopiesDo` compares
the `MODIFICATIONS` subtree of each embedded script against
`$NMSBONKER_REFERENCE_DIR/lua-src/<name>.lua`, all ten equal. `MOD_AUTHOR` is
compared separately and is `nmsbonker`, which is the one field that changed on
purpose. Golden stages A, B and C all pass unchanged.

**AC2 — a parameter change reaches the merged output by exactly the expected
factor.** Measured end to end on the real install, twice, into a scratch
workspace:

| | stock game file | `MATERIAL_MULTIPLIER = 10` | `= 20` |
| --- | --- | --- | --- |
| `AmountMin` | 3 | 30 | 60 |
| `AmountMax` | 10 | 100 | 200 |

`MODELS/SPACE/ASTEROIDS/SMALLASTEROID/ENTITIES/ASTEROID.ENTITY.MBIN`, decompiled
from each build's output with MBINCompiler. The value was changed with
`nmsbonker tweaks set MaterialYield10x MATERIAL_MULTIPLIER 20`; `git status`
reports `internal/tweaks/scripts/` unmodified afterwards, and
`TestSettingAParameterRecordsAnOverrideWithoutEditingTheScript` asserts the same
thing on the embedded bytes.

**AC3 — the symlink path.** On a fake game directory whose `GAMEDATA/MODS` is a
symlink to a directory holding one file:

```
nmsbonker: GAMEDATA/MODS is a symlink pointing at <target>. The game reads mods
through the link, so installing here would write into that directory instead of
the game. Pass --replace-symlink to remove the link (never its target) and
create a real GAMEDATA/MODS
```

exit 1. With `--replace-symlink`: `GAMEDATA/MODS` is a real directory holding
`COSMOS COMBINE/A.MBIN`, the former target still holds `PRECIOUS.MBIN`, and the
settings entry came back `Enabled=true`, `EnabledVR=true`,
`DisableAllMods=false`. The message names the symlink and nothing else;
`requireNeutral` in `internal/core/archive_test.go` asserts that mechanically
against a list of words it may not contain.

**AC4 — deploy twice, roll back, list, prune.** Two deploys produced two archive
entries (`archive list` shows both, the newer holding the first deployment's mod
folder and the older holding only the settings, since nothing was installed
before it). `rollback` put the first deployment back — the file in the game reads
`one` again — archived the second under a new timestamp, and left the workspace
still holding `two`. With seven older entries planted, the next deploy reported
`pruned: 6 older archive(s): …` and `archive list` came back with five.

**AC5 — the game's own switches.** A settings file with `DisableAllMods=true` and
the mod's entry off was deployed into; the diff is exactly three lines
(`DisableAllMods`, `Enabled`, `EnabledVR`), `file(1)` still reports "UTF-8 (with
BOM) text, with CRLF line terminators", and the unknown `SomeFutureSetting`
property is untouched. `mods-off` then `mods-on` returns the file byte for byte
to where it started (`TestModsOffAndModsOnFlipOnlyTheSwitch`). A second deploy
with nothing to change writes nothing at all.

**AC6 — save backup.** Run against the real Proton prefix into a scratch data
directory: 1 profile, 45 files, 12.2 MiB copied. The prefix held 45 files before
and 45 after; nothing in this code path opens a file there for writing.

**AC7 — install and uninstall.** `./install.sh` placed
`~/.local/bin/nmsbonker` (9,195,680 bytes), `~/.local/bin/nmsbonker-gui`
(27,108,904 bytes), `~/.local/share/applications/io.ushineko.nmsbonker.desktop`
and `~/.local/share/icons/hicolor/scalable/apps/nmsbonker.svg`.
`./uninstall.sh --dry-run` names those four and nothing else, and left all four
in place. `install.sh` was then run again — it is idempotent, and the app is
installed as this report is written. `desktop-file-validate` is clean.

**AC8 — docs and artifacts.** README rewritten (see below),
`docs/architecture.md` written, four screenshots in `assets/`, this report.
`make lint`, `make test`, the parity guard and the golden suites all pass.

**AC9 — the naming gate.** Two case-insensitive greps over the repository,
excluding `.git`, both come back empty: one for the superseded word this project
used for the parity oracle before spec 004 renamed it "the reference
implementation", and one for this machine's user name, its hostname, the path of
the reference pipeline and the path of the unrelated repository beside it. The
first term is deliberately not spelled here, since writing it down in a
committed file is exactly what the gate is checking for.

## Phase 4 — Code quality

**One place, one answer.** Three call sites needed "this mod's script with the
user's numbers in it" — the build, `mods check`, and the Tweaks section — so
there is one `session.scriptSource`, and what the parameter editor reports is by
construction what the build will load. The alternative, each of them applying
overrides its own way, is how a slider comes to show 20 while the build uses 10.

**Enabling a tweak is `SetModEnabled`.** `tweaks enable` and the Tweaks section's
checkbox call the same operation `mods enable` does. A tweak is a mod; giving it
a second code path would give it a second set of bugs.

**The archive layout changed** from spec 002's "the mod folder, at
`archive/<name>-<ts>`" to `archive/<name>-<ts>/{mod/,GCMODSETTINGS.MXML,archive.json}`,
because the entry now has to hold two things. `readArchiveEntry` still reads an
old-style directory rather than hiding it: it may be the only copy someone has of
what a deploy displaced.

**Dead weight removed:** nothing. `steam.ReadModSettings` is still the read path
`status` uses and `internal/modsettings` is the write path, which is one reader
too many — noted below as a limitation rather than fixed in a milestone commit.

## Phase 5 — Security review

**Verdict**: PASS

- **Dependency scan**: `govulncheck -mode=binary` on both binaries — **No
  vulnerabilities found** (tool from `~/go/bin`, Go 1.27.1 toolchain). No new
  module dependencies this phase: `go.mod`'s direct requirements are unchanged
  from phase 3.
- **New write paths into the user's world.** This phase is the first to write
  anywhere outside nmsbonker's own directories, so that is where the review
  went:
  - `GCMODSETTINGS.MXML` is written atomically (temp file plus rename) at 0644,
    which is the mode the game's own file already has, and only after the
    previous contents have been copied into the archive.
  - The mod folder is staged into `GAMEDATA/MODS/<name>.tmp-<pid>` and renamed,
    so an interrupted deploy leaves the previous mod intact rather than half of
    a new one.
  - `os.Remove` on a symlinked `GAMEDATA/MODS` removes the link, never the
    target; asserted by a test that checks the target's contents afterwards.
  - The save backup opens the Proton prefix read-only. Nothing in
    `internal/core/saves.go` writes into it, and the acceptance run counted the
    files there before and after.
- **Path handling.** Every path written comes from the resolved config or from
  the located install; the mod folder name is a config value and is escaped
  before it goes into an XML attribute (`Bits & Bobs` becomes `Bits &amp;
  Bobs`), which is the one place a setting reaches a document a third party
  parses.
- **The Lua sandbox is unchanged** and still the boundary a third-party script
  runs behind. Parameter substitution happens on the script *text* before it is
  compiled, so an override cannot inject anything a script could not already do:
  the value is written by `strconv.FormatFloat` from a `float64` and cannot
  contain a quote, a newline or a Lua token.
- **Secrets**: none in the changed code. `GITHUB_TOKEN` is still read from the
  environment only, never persisted and never logged.
- **Shell**: `shellcheck` clean on all three scripts. `install.sh` and
  `uninstall.sh` write only under `~/.local` and quote every expansion;
  `uninstall.sh` removes a fixed list of four paths.
- **The screenshot harness** writes to a fixed path under `$TMPDIR` and `rm -rf`s
  it. That is a predictable path, which on a shared machine is a symlink-attack
  surface; it is a developer tool run interactively on the machine that owns the
  repository, and the trade is that the paths it produces appear in a public
  README and have to read as examples rather than as `tmp.4Xk9aP`.

## Phase 5.5 — Release safety

| Question | Answer |
| --- | --- |
| How is the code undone? | `git revert`, then rebuild. No persisted format changed incompatibly. |
| How is a deploy undone? | `nmsbonker rollback` — the archive holds the mod folder *and* the settings as they were, five deep. |
| How is the whole thing undone? | `nmsbonker undeploy` removes the mod folder; `./uninstall.sh` removes the four installed files; the game is then stock apart from a `GCMODSETTINGS.MXML` entry naming a folder that no longer exists, which the game ignores. |
| What if the game will not start? | `nmsbonker mods-off` — nothing is removed and nothing has to be rebuilt. |
| Is the settings format compatible both ways? | Yes. `config.json` gains `params` and `save_backup`; an older binary preserves both through its unknown-key passthrough (spec 001 R2.1), and a newer binary reads a file without them as defaults. `report.json` gains `params`, and a report written without it is read as "no idea", which makes the Tweaks section say "unbuilt" — the safe direction. |
| Is anything deleted? | Archive retention deletes the sixth-oldest deploy and save retention the eleventh-oldest backup, both on a successful write of a newer one, and both print what they deleted. |
| Migration? | None. A configuration from phase 3 gains the ten built-ins, disabled, on the next `mods list`, and nothing else changes. |

**Not done, deliberately**: no version bump and no tag. `VERSION` stays `0.1.0`
and this report describes that milestone; tagging is the user's call.

## Limitations

- **No mid-build screenshot.** R7.3 asks for one of the Build section during a
  run. The window is a native Wayland client, `kdotool` can raise a window but
  cannot inject a click into one, and `nmsbonker-gui` has no flag that starts a
  build — adding one would be an operation with no CLI counterpart, which the
  parity rule forbids. Four sections were captured instead: Overview, Mods,
  Tweaks and Report, the last of them against a finished build.
- **Two readers for one file.** `steam.ReadModSettings` (spec 001, read-only,
  used by `status`) and `internal/modsettings` (this phase, read and write) both
  parse `GCMODSETTINGS.MXML`. They agree — the second is a superset of the first
  — but one of them should go, and doing it in the milestone commit was not worth
  the churn.
- **The tweak headers are hand-written.** A `@param` naming a global the script
  does not assign is caught by a test; a `@param` whose declared range is wrong
  for the game is not, and cannot be.
- **`Reset all to defaults` is not undoable.** It drops every override at once,
  behind a confirmation that says how many. The values it discards were the
  user's; nothing in the archive holds them.
- **Save restore is manual**, by design. Nothing here writes into the Proton
  prefix, and the listing prints the path to copy back to.
- **The window's Build section was not driven against the real game this phase.**
  Deploy, rollback, undeploy and mods-off were exercised against fake game
  directories in tests and by hand on the command line; nothing was deployed to
  the real install.
